## Context

K12-learn 的 MVP 目标是完成高中生物必修2题目知识点分类闭环：数据准备、BERT 训练、模型推理、Flask API、Vue 页面展示、MySQL 记录、Redis 缓存。当前仓库仍处于文档阶段，尚未形成工程结构。

参考项目 `D:\xuweiqun\py_project\work_heima\大模型三阶段\01_投满分\04-bert` 可以复用 BERT 文本分类思路，但不适合直接照搬：其配置、模型加载、路径和 API 耦合较重，训练和推理职责不清晰。新架构需要先建立清楚边界。

## Goals / Non-Goals

**Goals:**

- 搭建一个最小但可扩展的 Flask + Vue + BERT 项目骨架。
- 后端按 API、service、repository、ML、config 分层，方便后续逐步实现。
- 前端提供可演示的预测工作台，不做复杂后台。
- 训练脚本、推理模块和 Web 服务解耦。
- MySQL 和 Redis 配置通过 `.env` 或环境变量读取。
- 必要代码注释使用中文，帮助项目成员快速理解业务和架构意图。

**Non-Goals:**

- 不在本变更中要求完成真实模型训练效果优化。
- 不实现用户登录、权限、班级、学生画像或推荐系统。
- 不做线上部署、CI/CD、容器编排和高并发治理。
- 不实现复杂前端后台管理。

## Decisions

### 决策 1：采用前后端分离结构

项目根目录下分别建立后端和前端目录，例如 `backend/` 与 `frontend/`。后端提供 REST API，前端通过 Axios 调用。

备选方案是 Flask 直接渲染模板。该方案启动更快，但与 PRD 中 Vue 技术栈不一致，也不利于后续扩展页面。

### 决策 2：后端采用分层模块

Flask 后端按以下职责拆分：

- `api/`：路由、请求校验、响应格式。
- `services/`：业务编排，如预测、统计、知识点查询。
- `repositories/`：MySQL 数据访问。
- `ml/`：BERT 模型加载、推理、训练相关工具。
- `config/`：环境变量、路径、服务配置。
- `scripts/`：训练、数据校验、数据库初始化等一次性任务。

这样可以避免把模型推理、数据库写入和 HTTP 路由混在一个文件中。

### 决策 3：BERT 训练与在线推理解耦

训练脚本只负责读取训练数据、训练模型、输出模型文件和评估报告。在线推理模块只负责加载已保存模型并提供预测函数。

备选方案是把训练和推理都写在同一模块中。该方案早期代码少，但会导致 Web 服务启动时导入训练依赖和训练逻辑，运行风险更高。

### 决策 4：配置通过 `.env` 或环境变量读取

MySQL、Redis、模型路径、数据路径和服务端口都通过配置模块读取，不在业务代码中硬编码。PRD 中已明确默认开发配置，代码实现时将其落入 `.env.example` 和 README。

### 决策 5：前端页面先做单页工作台

Vue 前端 MVP 只做一个主工作台，包含输入、预测结果、知识点详情、最近记录、统计和健康状态。页面不引入登录和复杂导航。

### 决策 6：中文注释只用于必要位置

项目代码中的复杂业务、模型加载、配置回退、缓存降级和数据库初始化脚本需要使用中文注释说明意图。简单变量赋值、显而易见的函数调用不写注释，避免注释噪音。

## Risks / Trade-offs

- 数据量不足导致模型效果不稳定 → 先保证训练/预测流程可跑通，再逐步扩充样本。
- CPU 推理耗时较高 → 通过 Redis 缓存重复文本，后续再考虑模型压缩。
- 前后端同时搭建增加 MVP 工期 → 前端仅保留基础展示，不做复杂后台。
- 参考项目代码耦合较重 → 只复用模型思路，不复用硬编码路径和全局加载方式。
- `.env` 配置遗漏导致服务无法启动 → README 和 `.env.example` 必须列出必填项。
